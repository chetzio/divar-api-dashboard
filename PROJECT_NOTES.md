# رادیوکار (radiokar) — Project Notes

A personal business tool for the user's dad, who buys antique/old radios on Divar, keeps the good ones, and resells the rest (Divar, and soon Instagram) for profit. Not a client project — a birthday-gift side project. Persian/RTL, mobile-first, single user (dad), no auth.

**Phase 1 (this build, 2026-09-21) is complete and verified live**: financial tracking with repair/expense costs, a Contacts address book, email+SMS notifications, and a full visual redesign, on top of the original ledger/discovery/Telegram build from 2026-09-19/20. Phase 2 (Telegram bot as an *additional* interface — paste-a-link, quick-log by chat, `/stats`) is deliberately deferred; `worker/src/bot.ts` still exists and works, it's just not started unless `TELEGRAM_BOT_TOKEN` is set. See "Phase 1 additions" below for what's new; everything under "Repo layout" / "Kenar" / "Divar discovery" below describes the original build and is still accurate.

Full background/rationale for the architecture is in the conversation that built this (2026-09-19/20) — the short version: Divar's official **Kenar** developer platform (kenar.divar.dev, github.com/divar-ir/kenar-docs) is built for sellers managing their own listings, not buyers monitoring the marketplace. Its search API (`finder/post`) is capped at **100 calls for the app's entire lifetime**, so it can't power ongoing alerts. There's also no official webhook for new listings from other sellers. So the design splits into a reliable core (the ledger, zero API dependency) plus a best-effort discovery piece (polling Divar's own public feed, same approach community scraper projects use).

## Repo layout

npm workspaces monorepo:

- `web/` — Next.js 16 (App Router, Turbopack) + TypeScript + Tailwind CSS v4. The PWA dad actually uses. Server Actions for all writes (no separate REST layer). Dev port: whatever's free (see `.claude/launch.json` at the Projects root, entry `radiokar-web`, `autoPort: true` — don't hardcode a port in `web/package.json`'s dev script, Next.js 16 has a per-project lockfile that blocks a second `next dev` for the same dir regardless of port, so hardcoded ports just cause confusing conflicts).
- `worker/` — plain Node/TypeScript long-running process (run via `tsx`), not a web framework. Two independent jobs in one process: the Telegram bot (Telegraf, long-polling) and the Divar discovery poller. A Telegram outage does NOT take down the poller (see `worker/src/index.ts` — `bot.launch()` failure is caught and logged, discovery keeps running).
- `packages/core/` — shared TypeScript, consumed as source (no build step) by both `web` and `worker`. Both are ESM (`"type": "module"` in every package.json, including core's — **don't remove that**, without it Node's CJS interop silently drops named exports from core when the worker imports them, a real bug hit and fixed during the build). Holds: Prisma client singleton (`db.ts`), the official Kenar API client (`kenar.ts`), the unofficial Divar feed client (`divar-public.ts`), keyword filtering (`keywords.ts`), candidate promote/dismiss logic (`candidates.ts`), ledger stats (`stats.ts`), shared Persian formatters/labels (`format.ts`).
- `prisma/schema.prisma` — single schema, SQLite. Models: `Item` (the ledger row — status enum from `HUNTING` through `SOLD`; wishlist is just `Item`s with status `HUNTING`, deliberately not a separate entity), `SavedSearch`, `Candidate` (auto-discovered listings awaiting review), `Setting` (singleton row: Telegram chat id, Kenar API key, `finderCallsUsed` budget counter, plus Phase 1's `notifyEmail`/`notifyPhone`/`smsProvider`/`smsApiKey`), `Contact` (Phase 1), `Expense` (Phase 1, one-to-many off `Item`).
- Prisma client generates to `packages/core/generated/prisma` (explicit `output` in schema.prisma) — **do not upgrade to Prisma 7+** without deliberately migrating; Prisma 7 removed `datasource.url` from schema files entirely in favor of a new `prisma.config.ts` + driver-adapter pattern, which is a real breaking change hit during the build. Pinned to `6.19.3`.

## Environment files

Three copies of the same vars, all gitignored: root `.env`, `web/.env`, `worker/.env`. This isn't accidental duplication — Next.js only reads `.env` from `web/`'s own directory, `worker`'s dotenv only reads from `worker/`'s cwd, and Prisma CLI commands run from the repo root need a root `.env`. `DATABASE_URL` **must be an absolute path** (`file:C:/Users/.../radiokar/prisma/dev.db`), not relative — relative paths resolve inconsistently across the three cwds. `.env.example` at root documents this.

## Phase 1 additions (2026-09-21)

- **Contacts** (`Contact` model + `web/app/contacts/`) — an address book for recurring sellers/repair techs (`role`: SELLER/REPAIR/BUYER/OTHER). `Item.sellerContactId` and `Expense.contactId` optionally link to one, kept *alongside* the original freeform `sellerName`/`sellerPhone` text fields rather than replacing them — a one-off stranger seller stays freeform, linking to a saved Contact is only for people worth remembering. A contact's detail page shows every `Item` and `Expense` linked to them.
- **Expenses / financial tracking** (`Expense` model, UI on `items/[id]`) — repair/parts/shipping costs per item, each optionally tagged to a Contact ("who did this repair"). `packages/core/src/stats.ts`'s `getLedgerStats()` now subtracts each sold item's expenses from its profit and folds expenses into inventory cost, plus a new `getMonthlyProfit()` powering a small bar chart on the dashboard.
- **Notifications** (`packages/core/src/notify.ts` + `sms.ts`) — email via `nodemailer`/SMTP (creds in `SMTP_HOST`/`PORT`/`USER`/`PASS`/`FROM` env vars, needed in **both** `web/.env` — for the `/settings` "send test" buttons, which run as Server Actions in the `web` process — **and** `worker/.env` — for the actual alert loop) and SMS via a small per-provider adapter map in `sms.ts` (only `kavenegar` implemented so far; `notifyPhone`/`smsProvider`/`smsApiKey` are `Setting` fields entered through `/settings`, same trust model as the existing Kenar key field — adding Melipayamak/SMS.ir/Ghasedak later is one more entry in that map, not a rewrite). `worker/src/index.ts` no longer starts the Telegram bot by default — it only does if `TELEGRAM_BOT_TOKEN` is set (dynamic `import("./bot")`, so Telegraf isn't even loaded otherwise); the discovery loop's candidate callback fans out to email + SMS + (if running) Telegram, each independently try/caught so one channel failing can't block another or crash the poller.
- **Redesign** — new palette in `web/app/globals.css` (`--color-primary: #00788c`, `--color-secondary: #342a66`, plus the user's two greys `#7b7b7b`/`#a1a1a4`, and a near-black/off-white pair added for contrast the 4 given tones didn't cover on their own), light mode. Hand-drawn SVG line icons replaced the emoji nav in `NavBar.tsx`. Shared `.card`/`.btn-primary`/`.btn-secondary`/`.chip`/`.heading` utility classes in `globals.css` replaced the repeated inline class soup across every page.
  - **Font caveat**: a second display font (Lalezar, for headings) was tried and reverted. `next/font/google` fetches a font's files from `fonts.gstatic.com` the first time it's used, and this sandbox has no outbound access to that host (same restriction already noted below for `api.telegram.org`) — Vazirmatn kept working because it was already cached from earlier in the build, but Lalezar's fetch timed out and 500'd every page under Turbopack. Reverted to Vazirmatn's own heavy weight (`font-black`) for headings instead — zero extra network dependency, and arguably the right call anyway for a PWA loaded over a phone connection. If a second display face is still wanted, retry on a machine with normal internet access; nothing else needs to change.
- **CSV export** (`web/app/api/export/items/route.ts`) — a Route Handler, not a Server Action, specifically so a plain `<a href>` can trigger a real browser download with `Content-Disposition: attachment`. Includes a UTF-8 BOM prefix, without which Excel on Windows mis-renders the Farsi column headers/content as mojibake.
- **Collection Wall** (`web/app/collection/page.tsx`) — a photo-grid view of `status: KEEPING` items (dad's personal collection, not for-sale stock). Linked from the dashboard rather than given its own nav tab — Contacts already pushed the bottom nav to 6 tabs, a 7th felt like too many.

All of the above was verified through the *real* running app (not just code review): created a real Contact, linked it as an Item's seller, added an Expense tagged to that same Contact, marked the Item SOLD, and confirmed the dashboard's profit math, monthly chart, and CSV export all independently computed the identical correct number. Settings save/reload round-tripped correctly, and both "send test" buttons produced their intended graceful Persian error messages when SMTP/SMS weren't configured (as expected in this sandbox). The worker started cleanly and logged the expected "Telegram disabled, email/SMS active" message. Test data was deleted afterward so the ledger is empty for actual first use.

One tooling quirk hit during this verification, worth knowing if it recurs: the preview tool's `preview_click` did not reliably trigger Next.js `<Link>` client-side navigation or form submission via `<button type="submit">` in this environment — clicks reported success but nothing happened. Worked around it every time with `preview_eval` (`window.location.href = '/path'` for nav, `form.requestSubmit()` for submits). Not a bug in the app itself — confirmed by checking `window.location.pathname` and the network tab, which showed zero navigation/request activity from the clicks.

## The honest caveat: Divar discovery (`packages/core/src/divar-public.ts`)

This is the one unofficial, best-effort piece. `api.divar.ir/v8/postlist/w/search` is confirmed live and returns real current listings (title, token, city, image) with zero rate limit — but **it's unconfirmed whether the category/city filters in the request body actually do anything server-side**. Several guessed request shapes (based on a public Go client for a similar unofficial endpoint) were silently ignored in testing and returned the same generic nationwide feed regardless of what filter was sent. So the real filtering happens client-side via `matchesKeywords()` (`keywords.ts`) against whatever the feed returns — every `SavedSearch` currently polls the same nationwide firehose and is differentiated only by its keyword list, not by city.

**Next concrete step to improve this**: capture one real request from divar.ir's own search page via browser DevTools (Network tab, search for something, find the XHR to `api.divar.ir`, copy as cURL) and compare against what's implemented. Chrome extension wasn't connected when this was built, so this step is still open.

Verified working end-to-end during the build: a real `SavedSearch` row was polled live by the worker, the fetch succeeded with zero errors, `lastPolledAt` updated correctly. Zero candidates matched in that one sample, which is expected (radios are a small fraction of Divar's overall listing volume) — not a sign of failure.

## What's verified vs. not

- **Fully verified live**: web app (all 9 routes render at phone width — dashboard, items list/new/detail, contacts list/detail, finds, searches, settings, collection), full Contact↔Item↔Expense CRUD tested end-to-end through the real UI with correct profit math, monthly chart, and CSV export all agreeing on the same number, Prisma/SQLite, the Divar discovery poller's live fetch path, graceful worker degradation when Telegram is unreachable/unconfigured, the notification settings save/test-send round trip (with expected graceful failures since no real SMTP/SMS creds exist in this sandbox).
- **Structurally verified, not live-tested**: the Kenar API client (`getPost`/`searchPosts`) — code correctly implements the documented request/response shapes, but no real Kenar API key was available to test against; actually *sending* a real email or SMS (no real SMTP account or SMS provider key configured yet — the settings UI correctly reports this rather than silently failing); the Telegram bot — worker starts cleanly and registers all handlers, but this sandbox's network blocked outbound access to `api.telegram.org` (ECONNREFUSED, confirmed not a code issue), so live bot behavior needs testing on a real machine with a real token from @BotFather, when Phase 2 starts.
- **Not yet done**: real app icons (currently one SVG reused at all sizes — fine for most Android/Chrome install prompts, but real 192/512 PNGs would be more broadly compatible); deployment (VPS/domain didn't exist yet as of this build — see Build order in the original plan for the Docker Compose + Caddy + webhook-mode-switch steps); a second display font for headings (see the Lalezar caveat above); Phase 2 (Telegram bot re-enabled as an added interface).

## Setup checklist for the user

1. Register at kenar.divar.dev, create an app, get an API key → paste into the web app's `/settings` page.
2. For email alerts: an existing Gmail (or any SMTP-capable) account works — generate an App Password at myaccount.google.com/apppasswords, put the host/port/user/pass in **both** `web/.env` and `worker/.env` (see `.env.example`), then set the destination address on `/settings`.
3. For SMS alerts (optional, costs money per message): sign up with an Iranian SMS gateway — Kavenegar is the only one wired up so far — get an API key, enter phone/provider/key on `/settings`.
4. (Phase 2, not needed yet) Message @BotFather on Telegram, create a bot, get the token → put it in `worker/.env` as `TELEGRAM_BOT_TOKEN` to re-enable the Telegram interface alongside email/SMS.
5. `npm install` at repo root, then `npm run prisma:migrate` if the schema ever changes.
6. `npm run dev:web` and `npm run dev:worker` (separate terminals) for local dev.
